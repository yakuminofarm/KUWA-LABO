# アプリ版 (iOS / Android) の作り方

くわらぼは Web アプリとして作ってあり、それをそのまま Capacitor で包んで
iOS / Android アプリにする。画面や記録の仕組みは1つのままで、
出し先だけが2つに増える形。

## 2つの出し先のちがい

|  | ブラウザ版 (Vercel) | アプリ版 (iOS/Android) |
|---|---|---|
| 中身 | サーバあり | 端末に置いた静的ファイル |
| ニュース | 自分の `/api/news` | 公開中の配信を絶対URLで見にいく |
| Service Worker | 使う (オフライン用) | 使わない (最初から端末内にある) |
| 「テスト」表示 | 本番以外で出る | 出ない (本番あつかい) |

切り替えは環境変数 `NEXT_PUBLIC_KUWA_TARGET=native` の1つだけ。
`next.config.ts` と `src/lib/env.ts` が同じ値を見ている。

### なぜ `/api/news` はアプリ版に入らないのか

サーバがないと動かない口なので、静的な書き出しができずビルドが落ちる。
そこでファイル名を `route.web.ts` にして、ブラウザ版のときだけ
`pageExtensions` で拾うようにしてある。アプリ版は既定の拡張子のままなので
`route.web` は口として認識されず、自然に外れる。

アプリ版のニュースは公開中の `https://kuwa-labo.vercel.app/api/news` を
見にいく。別ドメインになるので、この口には CORS の許可を付けてある
(返すのは公開の見出しだけで、誰の記録も含まない)。
取れなければホームは雑学の一言に切り替わるだけで、記録の読み書きには影響しない。

別の場所に置いた口を使いたいときは `NEXT_PUBLIC_KUWA_API_ORIGIN` で変えられる。

## Mac 側の下ごしらえ (最初の1回)

```sh
# Xcode を App Store から入れる (15GB ほど。いちばん時間がかかる)
xcode-select --install
sudo xcodebuild -license accept

# Homebrew
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

# Node と CocoaPods (iOS のビルドに要る) と Android Studio
brew install node cocoapods
brew install --cask android-studio

# くわらぼを手元に
git clone https://github.com/yakuminofarm/kuwa-labo
cd kuwa-labo
npm ci
```

## 土台を作る (最初の1回)

`ios/` と `android/` は Mac の上で作る。中に Xcode / Android Studio の
プロジェクトが入るので、作った環境でしか正しく組み上がらない。

```sh
npm run build:native      # out-native/ に静的な一式が出る
npx cap add ios
npx cap add android
npm run assets:native     # アイコン・起動画面を assets/logo.png から作る
```

最後の `assets:native` を忘れると、`cap add` が Xcode の初期テンプレート
アイコン (青い X 印) のまま残ってしまう。ホーム画面に置いたときに
くわらぼのアイコンではなく Xcode 既定のアイコンが出る場合はこれが原因。

素材は `assets/logo.png` (背景を透過したクワガタ+二重螺旋) に入れてある。
`public/icon-512.png` (アプリの地色 `#eddcbb` で塗られた版) から背景色を
抜いて作ったもの。差し替えたいときはこのファイルを置き換えてから
`assets:native` をもう一度実行する。

## ふだんの流れ

画面を直したあとは、これだけで端末に反映できる。

```sh
npm run ios       # ビルド → 同期 → Xcode が開く
npm run android   # ビルド → 同期 → Android Studio が開く
```

内訳:

| コマンド | すること |
|---|---|
| `npm run build:native` | アプリ用に静的な一式を `out-native/` に書き出す |
| `npm run sync:native` | 上に加えて、iOS/Android のプロジェクトへ配る |
| `npm run ios` / `npm run android` | 上に加えて、Xcode / Android Studio を開く |

### 日付を選ぶ欄を日本語にする

日付の欄 (`<input type="date">`) をタップすると出てくる画面は iOS が用意する
もので、Web 側からは言葉を変えられない。iOS は**アプリが対応している言語**を見て
決めるが、Capacitor が作る `Info.plist` は `CFBundleDevelopmentRegion = en` で
`CFBundleLocalizations` を持たない。これだと英語専用のアプリと見なされ、
端末を日本語にしていても月の名前が `September` のまま出る。

`ios/` は Git に入れていないので手で直すと作り直したときに消える。
そこで `npm run sync:native` のたびに `scripts/patch-native-ios.mjs` が
当て直す (何度走らせても同じ結果になる)。同じ script でカメラの使い道
(`NSCameraUsageDescription`) も当てている。

実機に入れるところから先 (署名・証明書・ストアへの申請) は
Xcode と Android Studio の画面での作業になる。

`ios/` `android/` は Git に含めていないので、消して作り直したときは
「土台を作る」を最初からやり直す (`assets:native` も忘れずに)。

### 直したのに実機で変わらないとき

Xcode は `public` の中身だけが変わった場合、増分ビルドで見落とすことがある。
アイコンなどネイティブ側の差し替えは反映されるのに、画面の文言やレイアウトだけ
古いまま、という出方をする。

どこで止まっているかは、配った先のファイルを直接見れば分かる。
直したときに足した文字列を探す (例: `4.5rem`)。

```sh
grep -rl "探す文字列" ios/App/App/public/_next/static/chunks/
```

- **出てこない** → 配るところまで届いていない。`npm run ios` をやり直す
- **出てくる** → ファイルは新しい。Xcode が古いものを使っているので、
  Xcode で Product → Clean Build Folder (⌘+Shift+K) してから ▶

`npm run build:native` は書き出しのたびに `out-native/` を作り直すので、
Next 側のキャッシュが原因で古いままになることはない (確認ずみ)。

## 出す前に決めておくこと

- **`appId`** (`capacitor.config.ts`)。いまは `jp.yakuminofarm.kuwalabo`。
  ストアに出したあとに変えると別アプリ扱いになり、入れている人の記録が
  引き継げなくなる。出す前に決めきる
- **Apple Developer Program** 年 $99。iOS を配るのに要る
- **Google Play** 買い切り $25

## エサやりのお知らせ

出し先によって、鳴らし方が根本から違う。

| | ブラウザ版 | アプリ版 |
|---|---|---|
| やり方 | 開いている間だけ30秒ごとに見張る | 先の予定を端末に積んでおく |
| 閉じている間 | 鳴らない | 鳴る |
| 文面を決める時点 | 鳴らす直前 | 積むとき (先に決める) |

アプリ版は、鳴るときにアプリが動いているとは限らない。だから
`planFeedingNotices` (`src/lib/breeding.ts`) で、これから14日ぶんの
「その日に何頭たまっているか」を先に出し、`syncFeedingNotices`
(`src/lib/notify.ts`) で端末に積む。

数えるときは **「今日からあとは一度もエサをあげない」と仮定する**。
実際にあげれば、その記録をつけた時点で積み直すので数は減る。逆にすると
(あげる前提で数えると) あげ忘れた日に鳴らなくなる。鳴りすぎるより、
鳴らないほうが困る。

積み直すきっかけは、記録が変わったとき・設定を変えたとき・アプリに
戻ってきたとき。積んである予定は毎回すべて消してから積み直すので、
古い予定が残って実態と合わない知らせが鳴ることはない。

### 気をつけるところ

Capacitor のプラグインは、どんな名前のプロパティにも応答する作りに
なっている。`then` にも応答してしまうため、`async` 関数からプラグインを
そのまま返すと JS が「まだ解決していない約束」と勘違いして `then()` を
呼び、実装がないと言われて落ちる。`src/lib/notify.ts` では、プラグイン
本体ではなくそれを包んだモジュールのほうを返して避けている。

## 写真の置き場

記録は `localStorage` に置いてある。写真もそこに data URI で埋め込んでいたが、
1枚30〜50KBあるので100枚ほどで上限 (約5MB) に当たっていた。
さらに、エサやりを1件つけるだけでも全部の写真ごと書き直していた。

そこで **写真だけを記録の外に出し、記録は id で参照するだけ** にした。

| | ブラウザ版 | アプリ版 |
|---|---|---|
| 記録 | `localStorage` | `localStorage` |
| 写真 | IndexedDB (blob) | 端末のファイル (`Directory.Data`) |

### 成虫は何枚でも、幼虫は1枚

羽化直後と今、大あごの寄りなど、残しておきたい姿は1枚では足りない。
成虫は `photoIds: string[]` で持ち、**先頭が主な1枚** (一覧・個体カード・
血統書はこれを使う)。上限は6枚 — 1枚あたり大小2つで50KBほどなので、
切らないと1頭に何十枚も入れた人の端末だけが重くなる。

幼虫は1枚のまま。見た目で個体差が分かりにくく、何枚も残す意味が薄い。

写真の持ち方は3代ある。読む側は `src/lib/photoRef.ts` だけを通せば、
どの代の記録でも同じように読める。

| 形 | いつの形 |
|---|---|
| `photoIds: string[]` | いま |
| `photoId: string` | 1枚だけ持っていた頃 |
| `photoUrl: string` | 写真そのものを記録に抱えていた頃 |

### 1枚を大小2つで持つ

| | 長辺 | 使うところ |
|---|---|---|
| `<id>-s` | 320px | 一覧のサムネイル・登録画面のプレビュー |
| `<id>` | 1280px | タップして大きく見るとき |

大きいほうだけにすると、44pxのサムネイルのために1280pxを展開することになり、
50頭並べただけで数百MBのビットマップを抱えて端末が持たない。
小さいほうだけにすると大きく見たときに粗い。だから両方持つ。

移行してきた古い写真は長辺320pxしかないので、大きいほうとして入れてある。
欲しい大きさが無ければもう一方で代えるので、一覧でも詳細でも同じ1枚が出る。

記録そのものは1件200〜400バイト程度なので、写真が抜けた `localStorage` は
当分いっぱいにならない (1000頭でも300KB程度)。SQLite へ移す話は、
容量の面ではもう急がなくてよい。

窓口は `src/lib/photoStore.ts` ひとつで、出し先の違いはこの中に閉じてある。

### 気をつけるところ

**旧データの移行は起動時に1回だけ走る** (`src/lib/photoUpkeep.ts`)。
写真を置き場に書けたものだけ記録を差し替えるので、途中で失敗しても写真は
失われない (次の起動でやり直す)。バックアップから取り込んだ記録も
同じ形なので、同じ道を通る。

**迷子の写真の掃除も起動時だけ。** 登録をやめた写真や、記録を消したあとに
残った写真をここで片付ける。ただし追加画面で「写真を選んだがまだ保存して
いない」状態の写真は、どの記録からも参照されていないので迷子に見える。
復帰のたびに掃除すると、入力中の写真を消してしまう。

**バックアップのファイルの形は変えていない** (`version` は 1 のまま)。
書き出すときに写真を data URI へ戻して埋め込むので、1つのファイルで
完結したままで、古いくわらぼでも読める。

複数枚は **主な1枚を `photoUrl`、2枚目以降を `photoUrls`** に入れる。
`photoUrls` を知らない古いくわらぼでも、1枚は読める形にしてある。

**迷子の掃除は参照を数え上げる。** ここを1枚ぶんしか見ないと、2枚目以降が
どこからも参照されていないように見えて、起動のたびに消える。

## 個体カードの共有

個体の詳細から「この子を共有する」で、写真と要点をまとめた1枚の画像を作って
外へ渡せる。即売会の出品や、譲るときの受け渡しに使う。

| | ブラウザ版 | アプリ版 |
|---|---|---|
| 渡し方 | Web Share API | 端末の共有シート (`@capacitor/share`) |
| 使えないとき | 画像の保存に落とす | — |
| ファイルの置き場 | — | `Directory.Cache` (あとで消えてよい) |

**金額は載せない。** 入手金額と販売価格は人に見せるものではないので、
共有する1枚には入れない (`src/lib/shareCard.ts`)。何が載るかは
`cardRows` を試験から見張っているので、うっかり増やせば試験が落ちる。

### 高さを中身に合わせる

載る項目の数は個体によって変わる (産地や体長が空のこともある)。
縦を1350pxに決め打ちにすると、項目が6つある個体では表が下にはみ出して
羽化日が切れ、逆に項目が1つで写真も無い個体では下半分が空白になる。

そこで表の高さを先に出し、残りを写真に渡して、余ったら縦を詰める。
上限は縦4:5 (SNSで切られにくい形) で、それより縦長にはしない。

管理番号と愛称はどちらも長いことがあるので、見出しの幅を分け合う。
入りきらないぶんは「…」で切る (どちらかが消えることはない)。

### 気をつけるところ

やめたこと (共有シートを閉じた) と、渡せなかったことは区別している。
やめたときに「共有できませんでした」と出すと、失敗したように見えてしまう。
`shareCardImage` は `shared` / `saved` / `cancelled` / `failed` を返し、
画面では `saved` と `failed` のときだけ知らせる。

`@capacitor/share` も他のプラグインと同じ罠 (`then` に応答して落ちる) を
持つので、`src/lib/share.ts` ではモジュールのほうを返している。

## 血統書の書き出し

血統の欄に「血統書を書き出す」がある。本人と3世代ぶん (親・祖父母) を
A5の横1枚にして、共有シートか保存で外へ渡せる。即売会の出品や譲渡のときに、
画面を見せる代わりに渡すためのもの。

出し方は個体カードと同じ道 (`shareCardImage`) を通る。刷っても読めるように
1748×1240 (A5 横を 210dpi ほど) で作っている。

**これは自分の記録を書き写したもので、第三者の証明ではない。** 血統書という
名前は証明書のように見えるので、紙の上にもそう書いてある (`src/lib/pedigreeCert.ts`
の足元の注記)。この一文は消さないこと。

記録に無い先祖は、枠を省かずに点線の空枠で「記録なし」と出す。埋まっている枠だけ
並べると、家系のどこが分かっていないのかが受け取った側に伝わらない。

金額を載せないのは個体カードと同じ。`certRows` を試験から見張っている。

## 管理ラベルの印刷

データの持ち出しの中に「管理ラベルを作る」がある。選んだ成虫・幼虫の管理番号を
A4に等間隔で並べた画像を作り、共有シートから「プリント」へ渡せる。
菌糸ビンや成虫ケースに貼るためのもの。書き写す手間と取り違えが減る。

大 (21面・ケース向け) と小 (40面・ビン向け) の2つ。入りきらないぶんは
次の紙に回り、共有シートには複数のファイルをまとめて渡す
(`shareCardImages`)。

### 決めたこと

**市販のラベル用紙の枠には合わせていない。** A-one などは品番ごとに余白が
ミリ単位で決まっていて、そこに合わせると「その品番以外ではずれる」ものになる。
手元で確かめられないので、普通紙に刷って切る前提の等間隔の面付けにし、
切り取りの目安線を入れてある。

**予定は刷らない。** 次のビン交換の目安のようなものは入れない。紙は貼ったあと
直せないので、予定が変わると嘘になる。最後にビンを替えた日 (起きたこと) だけ。

**貼る先があるものだけ並べる。** 売った個体・飼育を終えた個体・成虫へ引き上げた
幼虫は出さない。貼る先がもう無い。

金額を載せないのは個体カード・血統書と同じ。試験で見張っている。

### QR付きのラベル

「QR付き (24面)」を選ぶと、各ラベルにQRが入る。アプリの成虫・育成の画面に出る
QRボタンから読み取ると、その記録が開く。棚の前でビンを持ったまま記録をつけられる。

**QRに入れるのは記録の id** (`kuwalabo:b:<id>` / `kuwalabo:v:<id>`)。
管理番号は後から書き換えられるし、同じ番号を2頭に付けてしまうこともあるので、
札としては使えない。読み取るのは自分のアプリの中だけなので、URLにする必要はない
(短いほうがQRの目が粗くなって読みやすい)。

**QRは刷る大きさを削れない。** 記録のidを入れると25目になり、まわりの余白を
足して33目。25mm四角に刷って1目0.76mmになる。ここを詰めると 0.5mm を割って
手元のカメラでは読めなくなるので、面を増やしたいときは面の数ではなく
**QRなしの型**を使う (`QR_SIZE` のコメントも参照)。

読み取りは `@capacitor/barcode-scanner`。アプリ版は端末のカメラ画面、
ブラウザ版は画面の中にカメラを出す (中で html5-qrcode を使う)。
読み取り機は大きい (360KBほど) ので、使うときまで読み込みを遅らせている
(最初の読み込みには入らないことを確認ずみ)。

**ブラウザ版では先にカメラを確かめる。** 読み取り機は自前の画面を開くが、
カメラが使えないと白い板が出たまま何も言わずに待ち続ける (許可していない・
カメラが無い端末で起きる)。`src/lib/scan.ts` で先に `getUserMedia` を試し、
駄目なときは自分の言葉で伝えてから諦める。

## 出品リスト

データの持ち出しの中に「出品リストを作る」がある。選んだ成虫をA4の表にして、
即売会の卓に置く一覧を作る。2種類ある。

| | 載るもの | 渡す相手 |
|---|---|---|
| 配布用 | 種類・産地・累代・性別・体長・羽化日 | お客さん |
| 手元用 | 上に加えて **原価** | 自分だけ |

値切られたときに下げてよい線は原価で決まるので、手元用には要る。
**紙の上に「お客さんに渡さないでください」と大きく刷ってある** — 刷ったあとに
取り違えると、仕入れ値を相手に見せることになる。配布用に原価の列が混ざらない
ことは試験で見張っている。

原価は、買ってきた個体は入手金額、自分で羽化させた個体は元の幼虫にかかった額
(引き上げのときに入手金額を写していないので、幼虫まで遡らないと出てこない)。

### 決めたこと

**出品価格の欄は作っていない。** いくらで出すかを前もって記録する習慣があるか
どうか分からないので、値段は手書きできるよう空けてある。当日の値付けは手書きの
ほうが早く、書き換えもきく。

**幼虫はまだ並べられない。** 即売会ではラインごとにまとめて出すことが多く、
1頭ずつの表とは形が違う。

**列の幅は最後の1つを残りから出す。** 全部決め打ちにすると、どれか1つを直した
ときに合計が紙幅とずれ、最後の列が切れたり余ったりする。

## 端末でしか確かめられないこと

ここまでの確認は、計算の部分の自動テストと、ブラウザ版が今までどおり
動くことまで。次は実機で見るしかない。

- 通知の許可を求める画面が出るか
- アプリを**閉じた状態**で、決めた時刻に鳴るか
- エサやりを記録したあと、鳴る予定が減っているか
  (Xcode のコンソールか、時刻を近くに設定して確かめる)
- 日付をまたいでも、翌日ぶんが正しく積まれているか
- 個体カードの共有・血統書・管理ラベルの書き出しで、端末の共有シートが開くか
